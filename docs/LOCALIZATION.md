# Localization contract

Maintenance Toolkit treats localization as an architectural requirement.

This contract is intended to remain consistent with the other Kraugh software projects unless a project documents a specific technical exception.

## Official languages

The official target language set is:

- Italian (`it-IT`);
- English (`en-US`);
- German (`de-DE`);
- French (`fr-FR`);
- Japanese (`ja-JP`);
- Simplified Chinese (`zh-CN`).

MT 4.0 currently provides the existing EN/IT localization foundation. Expansion to the complete official language set is planned work and must not be described as already implemented until it has been released and validated.

## Runtime selection

The application should:

1. detect the operating-system/user language at startup when language selection is automatic;
2. use the corresponding supported language resource when available;
3. fall back to English when the detected/requested language or an individual translation is unavailable;
4. allow an explicit supported-language override independently from the operating-system language.

## No hard-coded user-facing strings

MT-generated user-facing interface text must not be embedded directly in application logic.

User-facing text includes, where applicable:

- menus and commands;
- prompts and confirmations;
- status messages;
- warnings and errors generated by MT;
- labels and headings;
- report presentation text;
- help text shown by the application;
- newly introduced Inventory-related presentation text.

Such text must be resolved from external language JSON resources.

Native output produced by Windows or by an external tool is not an MT translation resource and should not be rewritten merely to satisfy this rule.

## Extensibility

Adding a new language, for example Spanish, should require adding a conforming language JSON resource rather than changing application logic.

Language resources must use a common key contract. Validation should detect:

- malformed JSON;
- unsupported language identifiers;
- missing required keys;
- duplicate or obsolete keys where practical.

A missing translation should degrade to the English value rather than breaking the application or exposing an unexplained raw key to the user.

## Stable technical contracts

Localization must not change machine-readable contracts.

The following remain stable and language-independent unless a separate versioned contract explicitly says otherwise:

- JSON schema field names;
- rule identifiers;
- module keys;
- exit codes;
- CLI parameter names;
- machine-to-machine values and enumerations;
- Inventory Schema field names and status values.

Localized UI may present translated labels for those concepts without changing their underlying identifiers.

## Documentation

Documentation languages and runtime UI languages are related but not identical requirements.

The repository uses English as the primary development/technical language. User documentation may have localized variants. Before every public release, the documentation gate must verify that published documentation accurately describes the languages actually supported by that release.

The public kraugh.it pages must also be reviewed from the current hosting source archive as required by `project/DEVELOPMENT_WORKFLOW.md`.
